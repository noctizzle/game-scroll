Make a game for Game Scroll

Every game in the feed is one small JavaScript file. Write yours, send it in, and once it's merged it streams to every player's phone within minutes, credited to you. No app update, no store review.

How it works

  1. Write one file. Your game lives in src/games/your-game.js. It draws on a canvas and reacts to touches. The app handles the rest: the start screen, the game-over screen, scores, credits, sizing for every phone.
  2. Try it on your phone. Run the app on your computer and open it on your phone over Wi-Fi.
  3. Open a pull request on GitHub. Automatic checks play your game in a headless browser, then Rob plays it.
  4. It goes live. When it's merged, your game streams into the feed for everyone, with your name on it.

You'll need some JavaScript. If you've made something with an HTML canvas before, you're ready. If not, copy the starter game below and change one thing at a time.

The rules

  • Original games only. Take inspiration from a genre or a mechanic (falling blocks, kart racing, platformers), but don't recreate a specific existing game: no copied names, characters, art, music, levels or look, even renamed.
  • A new mechanic. The goal is 1,000 games that each play differently. A reskin or harder version of a game already in the feed won't be merged. Play the feed and check the ideas list first.
  • Quick to learn, quick to play. A player should get it from a one-sentence hint. A round lasts about 20 seconds to 3 minutes.
  • Self-contained. One file, everything drawn in code. No image, font or sound files, no network requests, no tracking, no ads, no links out of the app.
  • Touch first. Every game must be fully playable with touch alone. Sensors are welcome as an extra.
  • Family friendly. Cartoon action is fine. No gore, hate, real-money gambling, or anything you wouldn't show a 12-year-old.

1. Get set up

Option A: on your computer

Install Node.js 22 or newer and Git. Then fork the repository on GitHub (you need a free GitHub account) and run:

git clone https://github.com/YOUR-NAME/game-scroll.git
cd game-scroll
npm install
npm run dev

Open the address it prints. On a desktop browser, Space starts a game, the arrow keys steer and ↓ goes to the next game. To try it on your phone, open the "Network" address on your phone while it's on the same Wi-Fi.

Option B: in your browser, nothing to install

Fork the repository, then on your fork click Code → Codespaces → Create codespace. You get an editor in the browser. In its terminal, run npm install and npm run dev, then open the forwarded port it offers. GitHub gives every account free Codespaces hours each month.

2. Write your game

Quickest start: npm run new my-game --style pocket writes a small game that already plays, in any style (phone, pocket, color, advance, console, nextgen or ar). Then make it your own.

Or start from scratch: create src/games/tap-bubbles.js (the file name must match the game's id). This is a complete, working game you can start from:

import { sfx } from '../sfx.js';
import { haptic } from '../kit/device.js';

const W = 360, H = 640;

function make(api) {
  let bubbles, score, t, missed;
  return {
    reset() { bubbles = []; score = 0; t = 0; missed = 0; },
    update(dt) {                       // dt is in seconds
      t += dt;
      if (Math.random() < dt * (1 + t / 10)) bubbles.push({ x: 30 + Math.random() * (W - 60), y: H + 30, r: 24 });
      for (const b of bubbles) b.y -= dt * (90 + t * 4);
      missed += bubbles.filter(b => b.y < -30).length;
      bubbles = bubbles.filter(b => b.y >= -30);
      if (missed >= 3) { haptic('warning'); api.over(); }
    },
    draw(c) {                          // a 2D canvas context, W x H units
      c.fillStyle = '#16212e'; c.fillRect(0, 0, W, H);
      c.fillStyle = '#5aa8ff';
      for (const b of bubbles) { c.beginPath(); c.arc(b.x, b.y, b.r, 0, 7); c.fill(); }
    },
    down(x, y) {                       // already in game units
      const i = bubbles.findIndex(b => Math.hypot(b.x - x, b.y - y) < b.r + 8);
      if (i < 0) return;
      bubbles.splice(i, 1); api.score(++score);
      haptic('light'); sfx(520 + score * 10, .06, 'triangle', .04);
    },
  };
}

export default {
  id: 'tap-bubbles', title: 'Tap Bubbles',
  tag: 'Casual · Reflex',             // "<Style> · <Genre>"
  retro: false, w: W, h: H,
  goal: 25,                           // the score that counts as a win
  hint: 'Pop the bubbles before they float away. Miss three and it is over.',
  make,
};

Then jump straight to it: open the browser console and run __gs.only('tap-bubbles'). Press ` (backquote) for the debug overlay: frame rate, slow motion, frame stepping and hitboxes.

What your game gets and gives

Your game objectWhen it's called
reset()Before every round. Put all round state here so "Play again" starts clean.
update(dt)Every frame while playing. dt is seconds since the last frame.
draw(ctx)Every frame. Draw the whole frame; nothing is cleared for you.
down / move / up(x, y, id)Touches, in game units. id tells fingers apart for two-thumb controls.
key(k, isDown)Optional keyboard support for desktop.
resize(w, h)Optional, for games that grow to fill big screens.

Your game calls api.score(n), api.over() and api.win(). To remember things between plays, like unlocked levels, use its own save slot: api.save(data) and api.load(fallback). Saves follow the player to a new phone.

The apiWhat it does
api.score(n)Sets the score. Reaching goal wins credits; the game keeps going.
api.over()Ends the round.
api.win()Wins right now, for games with a natural end.
api.has('item')True when the player bought that shop item for this run.
api.location()Where the player is, rounded. Needs location: 'coarse' in your game. Location games.
api.watchLocation(cb)Calls cb each time the player moves to a new spot, until the round ends.

The hint and the genre in tag also feed the recommender, so mention the control (tap, drag, tilt...) and the genre honestly.

3. Pick a style

Every game picks one of seven looks. The style sets the frame around your game, the start and game-over screens, and which tab it appears in.

Retro styles also set retro: true and a shell colour with pal. The 3D styles share one renderer, so never make your own WebGL context. The full contributor guide has the palettes, code samples for each style, and the 3D kits.

Big screens and foldables

Players use everything from small phones to unfolded Galaxy Z Fold and iPhone foldables, and can fold mid-game. By default your canvas is scaled to fit. To fill the extra space, add maxW and maxH and a resize(w, h) method; the app picks the best size and tells you. Keep the game fair at every size.

AR games: 3D in the player's real room

AR · 3D is the newest style. The back camera fills the screen and the phone's motion sensor turns the 3D camera, so a saucer, a bin or a hoop stays put in the room while the player moves their phone around. Shadows fall on the real floor. It's "look-around" AR: players turn, tilt and look up and down on the spot, but walking isn't tracked.

The games in the feed now show what works: Saucer Swarm (turn to aim, tap to zap saucers swooping round the room), Bin Flick (flick paper balls into a bin on your floor) and Hoop Drone (fly a tiny drone through glowing hoops wherever you point).

The AR kit

AR games use src/kit/ar3d.js, built on the Next Gen HD renderer, so you get real materials, reflections and shadows. A minimal AR game looks like this:

import { want } from '../kit/device.js';
import { ARView, arNote, FLOOR } from '../kit/ar3d.js';
import { pbr, rbox, THREE } from '../kit/hd3d.js';

function make(api) {
  want('motion');                      // iPhones ask for motion access on the Play tap
  let v;
  return {
    reset() { v?.off(); v?.recenter(); /* set up the round */ },
    update(dt) { if (!v) return; v.live(); /* game logic; v.off() before api.over() */ },
    draw(c) {
      if (!v) { v = new ARView(); /* build meshes, add them to v.scene */ this.reset(); }
      v.look();                        // motion sensor (or drag) turns the camera
      v.draw(c, W, H);                 // camera picture + your 3D scene
      v.pointers(c, W, H, [{ p: target, col: '#8affdc' }]);   // arrows to things off screen
      arNote(c, v, W, H);              // says when a fallback is on
    },
  };
}

export default {
  id: 'my-ar-game', title: 'My AR Game', tag: 'AR · Shooter',
  retro: true, era: 'ar', pal: 'grape',
  w: 300, h: 460, maxW: 600, maxH: 680,
  goal: 20, hint: 'Turn your phone to aim... No camera? Drag to look around.', make,
};

Making it feel real

  • Use real sizes and distances. The phone is the eye, about 1.3 m above the floor (FLOOR is -1.3) and straight ahead is -z. Put things 1.5 to 7 m away at their real size: a bin is about 38 cm tall, a saucer 80 cm across.
  • Make players turn. Spread targets all round them, behind too, and always add edge arrows with v.pointers() so they can find them.
  • Use the helpers. v.forward(), v.heading() and v.offAim(p) tell you where the phone points; v.toScreen(x, y, z) gives screen positions for taps and labels.
  • Keep it phone-friendly. AR shares the one 3D renderer with the console games, so keep meshes few and simple.

Fallbacks are required

Every AR game must play everywhere. With no camera (refused, or on a computer) the kit draws a virtual room instead. With no motion sensor, the player drags to look around (v.drag(dx, dy)); if dragging is already your control, keep targets in view instead. Stop the camera with v.off() in reset() and before api.over(). The camera picture is never saved or sent.

Test the fallback path with the usual checks (smoke, fold, sweep), then try it on a real phone, because the camera and motion sensor only work there. The full reference, including how to fake a camera in a headless browser, is in docs/ar-3d.md.

4. Sound, haptics and phone sensors

Import shared helpers from the app; it hands them to streamed games. A game can't import any other app code.

  • src/kit/sound.js: ready-made sounds like sounds.coin() and sounds.boom(), explosions, jingles and looping music.
  • src/kit/juice.js: particles, screen shake, smooth movement and "+10" pop-ups.
  • src/kit/controls.js: thumbsticks, buttons, two-thumb layouts, and tap, hold and swipe detection.
  • src/kit/physics2d.js: balls and boxes that bounce, stack and collide.
  • src/sfx.js: sfx(freq, duration, type, volume) for short synth sounds. Respects mute.
  • src/kit/device.js: haptic(), buzz(), tilt(), onShake(), heading(), faceDown(), startMic(), startCamera().
  • src/kit/geo.js: distance(), bearing(), offset(), toLocal() and cellId() for location games.
  • src/util.js and src/palettes.js: maths helpers, pixel sprites, palettes.

The maker kit guide explains all of these with examples.

Sensors return nothing in the browser or when a player says no, so every sensor game needs a touch fallback: drag instead of tilt, tap instead of shout. Stop the mic or camera when the round ends. Location, camera and mic data must never leave the phone.

Location games

A game can build its level from the player's area (a daily puzzle shared with everyone nearby, local weather, monsters that live in this park) or be played by walking around. Say how precise it needs to be in the game definition:

export default { id: 'park-hunt', /* ... */ location: 'coarse', make };   // or 'precise' for walk-around games

// inside make(api), during play (for example in update, the first time it runs):
api.location().then(here => {
  // { lat: 51.51, lon: -0.13, accuracy: 1100, real: true, precision: 'coarse' }
  // or the stand-in { lat: 0, lon: 0, real: false, reason: 'denied' | 'off' | 'unavailable' | 'not-playing' }
  buildLevel(here.real ? cellId(here, 2000) : dailySeed);   // cellId from src/kit/geo.js
});
  • Rounded for you. 'coarse' (use this unless you truly need more) rounds to about 1 km. 'precise' rounds to about 10 m, for games played by walking, and a maintainer checks it's needed.
  • Only during a round. The phone asks the first time a player presses Play on a location game, never before. Before Play and after the round you get the stand-in. The feed tells players "Uses your rough area" on the start screen.
  • Always playable. When the player says no, switches it off in Settings, or is indoors with no fix, you get real: false. Fall back to a daily seed, or let the player walk the stand-in around by touch with offset(here, east, north).
  • api.watchLocation(cb) calls cb straight away and each time the rounded spot changes. It stops by itself when the round ends; it also returns a stop().
  • Never read navigator.geolocation yourself, and location never leaves the phone. There are no map tiles yet, so draw the area yourself.
  • Older versions of the app don't have this, so they skip location games until they update.

5. Credits and shop items

Winning any game pays credits, which is why goal is required. Pick a goal a decent player reaches in about a minute. You can also sell items for credits:

reward: 10,   // credits per win; the first win pays double
shop: [
  { id: 'shield', name: 'Shield', price: 25, kind: 'boost', desc: 'Survive one crash.' },
  { id: 'gold', name: 'Gold Skin', price: 150, kind: 'unlock', desc: 'Forever gold.' },
],
// in your game: if (api.has('shield')) { ... }

6. Test it

Play it on a real phone if you can: check the controls feel good with a thumb, the hint makes sense, and the goal is reachable. Then run the same checks the pull request runs:

npm i --no-save playwright && npx playwright install chromium   # first time only
npm run build:bundled
node scripts/smoke.cjs tap-bubbles    # plays it with random input; fails on any error
node scripts/fold.cjs tap-bubbles     # folds and unfolds the screen mid-game
node scripts/sweep.cjs tap-bubbles    # long play at odd sizes (needed for 3D and AR games)
npm run games                         # fails if the file name and id differ

7. Submit it

  1. Commit your game file on a branch of your fork and push it.
  2. On GitHub, open a pull request against main of robthewizzuk/game-scroll.
  3. Fill in the template: what the game is, why its mechanic is new, its style, and a screenshot or short clip.
  4. The automatic checks build the app and play your game. Fix anything they flag.
  5. Rob plays it and may ask for changes. Games that break the rules or play too much like one already in the feed may be turned down.

A game pull request should only add or change your file in src/games/. Changes to shared code ship inside the app and need an app update, so open those separately and explain why.

After it's merged

You don't need to do anything. Every merge builds each game as its own small file and uploads it with a new catalogue. Phones check the catalogue regularly, so your game appears in feeds within minutes, credited to you by your GitHub name. Fixes reach players the same way.

Games that turn out weak or broken in play testing may be hidden or removed later.
